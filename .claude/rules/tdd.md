# TDD Rule

> **이 규칙은 Rigid다.** 상황에 맞게 변형하거나, "이번만 예외"를 만들지 마라.
> 단, 프로젝트의 `CLAUDE.md`/`AGENTS.md`에 이 프로젝트 전용 TDD 규칙이 명시되어 있다면 **그쪽이 우선**한다. 이 파일은 그런 규칙이 없을 때 적용되는 **fallback 기본값**이다.

## 1. 적용 기준

### TDD를 반드시 적용해야 하는 대상
- 비즈니스 로직 (계산, 상태 전이, 조건 분기)
- API 엔드포인트 / 서버 핸들러
- 유틸리티 함수 (순수 함수, 데이터 변환/정규화)
- 버그 수정 (실패하는 재현 테스트 → 수정)

### TDD가 불필요한 대상
- 타입 정의 (interface, type alias)
- 설정 파일 (config, env, build 스크립트)
- 순수 UI (마크업/스타일만 있고 로직 분기가 없는 프레젠테이션 컴포넌트)
- SQL / 마이그레이션 스크립트

애매하면 "이 코드가 잘못된 값을 반환하거나 잘못된 상태를 만들 수 있는가?"로 판단한다. 그럴 수 있으면 적용 대상이다.

## 2. RED-GREEN-REFACTOR 사이클

### RED
- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 테스트에 몰아넣지 마라.
- 테스트를 작성한 즉시 **반드시 실행해서 실패를 눈으로 확인**한다.
- 실패 이유는 반드시 **"기능이 아직 구현되지 않았기 때문"**이어야 한다. 오타, import 누락, 잘못된 assertion 때문에 실패한 것이라면 그건 유효한 RED가 아니다.

### GREEN
- 테스트를 통과시키는 데 필요한 **최소한의 코드만** 작성한다. **YAGNI** — 지금 테스트가 요구하지 않는 기능/분기/추상화를 미리 만들지 마라.
- 통과 여부를 신규 테스트 하나만으로 판단하지 말고, **신규 + 기존 테스트 전체**를 실행해 모두 통과하는지 확인한다.

### REFACTOR
- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- 리팩터링 동안 **green을 유지**한다 — 테스트가 깨지면 즉시 되돌린다.
- 이 단계에서 **새로운 동작을 추가하지 마라.** 새 동작이 떠오르면 다음 사이클의 RED로 넘긴다.

### 반복
REFACTOR가 끝나면 다음 동작에 대한 **RED로 돌아간다.** 사이클 순서를 건너뛰지 마라.

## 3. 삭제 강제 규칙

- 테스트보다 프로덕션 코드를 먼저 작성했다는 사실을 발견하면, **그 프로덕션 코드를 삭제하고 RED부터 다시 시작**한다.
- "일단 참고용으로 남겨두고" 주석 처리하거나 다른 파일로 옮기는 것도 금지한다. 삭제하고 처음부터 다시 간다.

## 4. 변명 차단표

| 변명 | 반론 |
|---|---|
| "너무 단순해서 테스트가 불필요하다" | 단순한 코드일수록 테스트 작성 비용도 가장 낮다. 단순함은 생략의 근거가 아니라 작성 쉬움의 근거다. |
| "나중에 테스트를 추가하겠다" | "나중"은 오지 않는다. 테스트 없는 코드는 이미 프로덕션에 들어간 순간 우선순위에서 밀린다. |
| "시간이 없다" | 테스트 없이 짠 코드는 디버깅 시간으로 그 대가를 반드시 치른다. 지금 쓰는 시간이 나중에 버그를 찾는 시간보다 짧다. |
| "이미 짠 코드를 삭제하면 낭비다" | 검증되지 않은 코드는 자산이 아니라 부채다. 삭제 비용은 그 부채가 프로덕션에서 터졌을 때의 비용보다 항상 작다. |
| "이건 프로토타입이라 상관없다" | 프로토타입은 살아남아 프로덕션이 된다. "임시"라는 이름표는 코드의 실제 수명을 바꾸지 못한다. |

## 5. 우선순위

이 파일은 fallback이다. 작업 중인 프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 관련 규칙(테스트 대상 범위, 테스트 프레임워크, 예외 조건 등)이 명시되어 있으면 그 규칙을 따르고, 이 문서와 충돌하는 부분은 무시한다.
