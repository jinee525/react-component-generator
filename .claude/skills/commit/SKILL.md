# Commit

## 언제 사용하는가

사용자가 "커밋해줘", "커밋", "변경사항 커밋", "저장해줘" 등으로 커밋을 요청할 때 이 스킬을 따른다. 목표는 `git commit -m "..."` 한 줄을 실행하는 게 아니라, 변경사항을 의미 단위로 정리해서 나중에 `git log`만 봐도 무엇이 왜 바뀌었는지 알 수 있게 만드는 것이다.

## 절차

### 1. 변경사항 파악

- `git status`로 추적되지 않은 파일까지 포함해 전체 상태를 본다.
- `git diff` (unstaged)와 `git diff --staged` (staged)로 실제 변경 내용을 읽는다.
- `git log --oneline -10`으로 최근 커밋 메시지 스타일을 확인한다. 이 저장소만의 컨벤션(스코프 표기, 이모지, 영어 사용 등)이 이미 있다면 그것을 우선하고, 특별한 컨벤션이 없을 때만 아래 기본 포맷을 쓴다.

### 2. 논리적 단위로 분류

변경된 파일들을 살펴보고 서로 독립적인 의도를 가진 덩어리로 나눈다. 예를 들어 새 기능 추가와 별개의 버그 수정이 같이 섞여 있다면 이는 두 개의 커밋이 되어야 한다 — 하나의 커밋에 여러 목적이 섞이면 나중에 `git blame`이나 되돌리기(revert)를 할 때 무엇을 되돌려야 할지 알기 어려워지기 때문이다.

판단 기준:
- **같은 단위로 묶는다**: 구현 코드와 그에 대한 테스트, 리팩터링과 그로 인해 필요해진 호출부 수정, 한 기능을 위해 여러 파일에 걸쳐 이뤄진 일관된 변경
- **다른 단위로 나눈다**: 서로 다른 기능, 관련 없는 버그 수정, 포맷팅/설정 변경과 기능 변경이 섞인 경우

단위가 하나뿐이면 커밋도 하나만 만든다. 억지로 쪼개지 않는다 — 쪼개는 이유는 히스토리 가독성이지, 커밋 개수를 늘리는 것 자체가 목적이 아니다.

### 3. 각 단위별로 커밋 메시지 작성

각 논리 단위에 대해 다음 형식으로 한국어 커밋 메시지를 작성한다:

```
<type>: <한 줄 요약>
```

- `type`은 실제 변경 성격에 맞춰 고른다: `feat`(새 기능), `fix`(버그 수정), `refactor`(동작 변화 없는 구조 개선), `chore`(빌드/설정/문서 등 그 외).
- 요약은 "무엇을 했는지" 나열이 아니라 "왜/무엇을 위해 했는지"가 드러나는 간결한 한국어 평서문으로 쓴다.
- 필요하면 본문을 추가해 배경을 설명해도 되지만, 짧은 변경은 제목 한 줄이면 충분하다.

### 4. 사용자 승인 후 커밋

커밋을 실행하기 전에 계획을 먼저 보여준다: 몇 개의 커밋으로 나눌지, 각 커밋에 어떤 파일이 포함되는지, 각 커밋 메시지가 무엇인지. 사용자가 승인하면 그때 단위별로 `git add <해당 파일들>` 후 `git commit`을 실행한다. `git add -A`나 `git add .`처럼 통째로 스테이징하지 않는다 — 무관한 파일이 실수로 같이 커밋되는 것을 막기 위해서다.

스테이징하기 전에 `.env`, `credentials.json` 같은 민감한 파일이나, 이름은 평범해도 내용에 비밀키·토큰이 들어있는 파일이 포함되지 않았는지 확인한다.

## 지켜야 할 것

- 사용자가 명시적으로 요청하지 않는 한 `--no-verify`, `--amend`, `push --force`는 쓰지 않는다.
- pre-commit 훅이 실패하면 원인을 고치고 새 커밋으로 다시 시도한다. 실패한 시도를 amend로 덮어쓰지 않는다.
- 커밋 메시지는 heredoc으로 전달해서 줄바꿈과 특수문자가 깨지지 않게 한다:
  ```bash
  git commit -m "$(cat <<'EOF'
  feat: 사용자 인증 기능 추가
  EOF
  )"
  ```
- 커밋 개수와 계획이 확정되기 전까지는 실제 `git commit`을 실행하지 않는다.
