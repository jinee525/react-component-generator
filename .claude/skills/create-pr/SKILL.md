# create-pr: 역할별 PR 생성

퍼블리셔·FE 개발자·서버 개발자는 PR에서 확인해야 할 것이 다르다(스크린샷·접근성 체크리스트 / 테스트·타입 체크 / API 하위호환성·보안). 이 스킬은 역할을 먼저 확정한 뒤, **그 역할에 해당하는 템플릿 파일만** `templates/` 아래에서 읽어 그 기준으로 PR을 만든다. 세 역할의 템플릿을 동시에 다 읽지 않는다 — 실행은 매번 격리된 서브에이전트(`context: fork`)에서 이뤄지고, 이 스킬이 가진 도구는 읽기·검색·git/gh 명령으로 한정된다(소스 코드를 직접 수정하지 않는다).

템플릿 파일:

- [templates/publisher.md](templates/publisher.md) — 퍼블리셔(마크업/디자인 구현)
- [templates/fe.md](templates/fe.md) — FE 개발자(로직/상태 구현)
- [templates/server.md](templates/server.md) — 서버 개발자(API/백엔드 로직)

## 워크플로우

### Step 0: 저장소 지침 로드

저장소 루트의 `AGENTS.md`(없으면 `CLAUDE.md`)를 읽는다. 하위 디렉토리에 중첩 `AGENTS.md`(예: `server/AGENTS.md`, `src/AGENTS.md`)가 있고 이번 변경이 그 범위에 속하면 그것도 함께 읽는다. PR 관련 규칙(제목 컨벤션, 필수 체크 등)이 이미 명시돼 있으면 그것이 아래 역할별 템플릿보다 **우선**한다.

### Step 1: 역할 확정

`$ARGUMENTS`의 첫 토큰이 `publisher`, `fe`, `server` 중 하나인지 확인한다.

- 셋 중 하나면 그 역할로 확정한다.
- 없거나 다른 값이면 **추측하지 말고** `AskUserQuestion`으로 "퍼블리셔 / FE 개발자 / 서버 개발자" 중 선택하게 한다.

### Step 2: 역할별 템플릿 로드

확정된 역할에 해당하는 파일만 읽는다: `templates/publisher.md`, `templates/fe.md`, `templates/server.md` 중 하나.

이 파일의 PR 제목 형식, 본문 템플릿, 체크리스트, 리뷰어 안내를 이후 전 단계에서 그대로 따른다. 템플릿이 "초안(draft)"이라고 표시돼 있으면, 사용자가 실행 중 다른 값을 알려줄 경우 그것을 우선한다(파일을 그 자리에서 고치지는 않는다 — 갱신은 사용자가 명시적으로 요청할 때만).

### Step 3: 변경사항 파악

- `git status`, `git diff`, `git diff --staged`로 현재 변경 상태를 확인한다.
- `git log --oneline <base>..HEAD`로 이번 PR에 포함될 커밋 전체를 확인한다(마지막 커밋만 보지 않는다).
- 현재 브랜치가 원격에 푸시돼 있는지, 이미 열린 PR이 있는지 `gh pr view` 등으로 확인한다.
- 커밋되지 않은 변경이 있으면 먼저 커밋이 필요함을 알린다(커밋 자체는 이 스킬의 책임이 아니다 — 저장소에 `commit` 스킬이 있으면 그것을 쓰도록 안내한다).

### Step 4: 체크리스트 대조

Step 2에서 로드한 체크리스트 항목을 실제 diff와 대조해 어떤 항목이 충족됐고 어떤 항목이 비어있는지 정리한다(예: FE 템플릿인데 테스트 변경이 없다, 퍼블리셔 템플릿인데 스크린샷을 아직 첨부 못했다, 서버 템플릿인데 하위호환성 언급이 없다). 비어있는 항목이 있으면 목록으로 알리고, 그래도 진행할지 사용자에게 확인한다 — 임의로 항목을 생략하거나 충족된 것처럼 꾸미지 않는다.

### Step 5: PR 제목·본문 작성

역할 템플릿의 형식을 그대로 사용해 제목과 본문 초안을 작성한다. 본문은 Step 3에서 확인한 실제 커밋/변경 내용을 요약하되, 체크리스트는 Step 4에서 실제로 확인된 상태로 채운다(미확인 항목은 체크하지 않은 채로 둔다).

### Step 6: 사용자 승인

작성한 제목·본문·리뷰어 후보를 사용자에게 보여주고 승인을 받는다. 이 시점 이전에는 push나 `gh pr create`를 실행하지 않는다.

### Step 7: 실행

승인 후:

1. 현재 브랜치가 원격에 없거나 뒤처져 있으면 푸시한다(`git push -u origin <branch>`). force-push는 사용자가 명시적으로 요청하지 않는 한 쓰지 않는다.
2. `gh pr create --title "..." --body "$(cat <<'EOF' ... EOF)"` 형식으로 본문 줄바꿈이 깨지지 않게 생성한다.
3. 템플릿에 리뷰어가 명시돼 있으면 `gh pr edit --add-reviewer`로 지정한다. 리뷰어를 특정할 수 없으면 사용자에게 직접 묻는다.

### Step 8: 결과 보고

생성된 PR URL과 Step 4에서 확인되지 않았던 체크리스트 항목(있다면)을 함께 보고한다.

## 지켜야 할 것

- 역할을 추측하지 않는다 — 인자가 없으면 반드시 묻는다.
- 세 역할의 템플릿을 동시에 섞어 쓰지 않는다. 변경 내용이 마크업·프론트 로직·서버 로직 여러 영역에 걸쳐 있으면, 사용자에게 어느 템플릿 기준으로 낼지 확인하거나 PR을 분리할지 물어본다.
- `--no-verify`, `--force`, `push --force`는 사용자가 명시적으로 요청하지 않는 한 쓰지 않는다.
- 이 스킬은 소스 코드를 수정하지 않는다(`allowed-tools`에 Edit/Write가 없다). 체크리스트 미충족 항목을 발견해도 코드를 고치려 하지 말고 사용자에게 알린다.
